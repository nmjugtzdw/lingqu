> 版本：v1.0.0　｜　日期：2026 年 11 月

## 一页摘要

**一句话**：灵渠把数据库同步做成了一件「可以验收、可以回退、出问题找得到人」的交付件，而不只是一个能跑起来的程序。

**您能感受到的变化**

- 装好就是中文，电脑和手机浏览器都能用；建任务一步一页，随时存草稿，下次接着填
- 正式写入之前先体检、先只读试跑，不会一上来就动目标库
- 每一步都有记录，任务跑完能导出报告留档、复核、交接
- 升级不用改业务库；真要回退，有写好的顺序可以照着做

**验证情况**：发布基线 5,111 项自动化检查全部通过，零失败、零报错；在真实 SQL Server → MySQL 环境完成 10 万行同步，平均每秒 5.2 万行；四种数据库链路逐一实测，发现并修复 4 项缺陷。

**下载与支持**：安装包与校验值见 GitHub Releases 的 v1.0.0；从 0.2.0 升级只需备份数据目录后替换程序文件。使用中遇到问题，可用产品内「报告问题」入口，或到社区交流反馈。

## 1　这份材料要回答的三个问题

评估一套同步工具时，真正难回答的往往不是「支持多少种数据库」，而是：

1. 它会不会动坏我的库？
2. 它说同步完了，我凭什么信？
3. 半夜出问题，怎么定位、怎么退回去、谁负责？

功能清单回答不了这三个问题。灵渠的做法是：把每个阶段的验收证据固定下来，并且**把没做到的部分也写清楚**。下文按这三条展开。

---

## 2　交付是怎么被验收的

灵渠的开发分为 **15 个阶段**：从基础审计、连接与元数据、全量装载、增量同步、调度与检查点、体检与备份，到任务驾驶舱、问题处理、完成报告、稳定性与发布验收。

每个阶段结束后，必须提交一份**固定 12 项的验收记录**，缺一项就不能算完成：

| # | 记录项 | 这一项替您守住什么 |
|---|---|---|
| 1 | 阶段 | 做到哪一步，不混入下一阶段的工作 |
| 2 | 状态 | 只有「已完成 / 基线完成 / 部分完成 / 未开始 / 阻塞」五种。**检查全绿不等于阶段完成**，还要有交付内容、记录与真实数据库证据 |
| 3 | 交付版本标记 | 出问题时能定位到具体是哪一版 |
| 4 | 数据库结构版本 | 判断这次升级会不会动业务库 |
| 5 | 改动清单 | 影响面有多大，哪些文件被动过 |
| 6 | 新增检查项 | 这一阶段补了哪些防护，删掉的检查必须说明理由 |
| 7 | 检查命令与结果 | 贴真实数字与实际结果，可复现，不是口头一句「测过了」 |
| 8 | 真实数据库环境与结果 | 写明用什么库、初始状态、实际观测；不能只在模拟环境里跑 |
| 9 | 安全结论 | 逐项回答：凭据有没有进日志、有没有新增越权路径、破坏性操作有没有二次确认 |
| 10 | 已知限制 | **必须写**。写清哪些是刻意不做、哪些是能力缺口、哪些是「只保证了 A，B 尚未覆盖」 |
| 11 | 回滚步骤 | 具体可执行的退路，不是「回滚即可」 |
| 12 | 验收人与日期 | 谁签字、哪一天 |

**签字栏由项目负责人填写，开发方不代签。** 这条规矩看起来小，却是整套记录能不能被追责的关键。

这套东西难复制的地方不在于流程复杂，而在于它要求每次交付都留下「没做完的部分」。功能可以照着做，签字、退路和已知限制，只有在真实项目里才会长出来。

## 3　验证数据（口径逐一交代）

| 项目 | 结果 | 口径说明 |
|---|---|---|
| 发布基线全量自动化检查 | **5,111 项，0 失败、0 报错、5 项按设计跳过** | 界面收敛后的最终发布基线，2026-11-11 |
| 缺陷修复候选包全量检查 | **5,124 项，0 失败、0 报错** | 早一轮基线，在缺陷修复后执行 |
| 真机性能 | 真实 SQL Server → MySQL，**10 万行，平均 52,548.6 行/秒** | 2026-11-08，单表全量装载，源与目标行数逐位一致 |
| 真实数据库链路 | MySQL、PostgreSQL 16、SQL Server 2019、Oracle 23.6 Free **共 4 条** | 每条覆盖全量装载、增删改实时捕获、模拟断网后续传、重启后接着跑、权限拒绝、源表结构变化自动暂停 |
| 备份与恢复 | 通过 | 从备份恢复后，连接配置、任务配置与同步位置均可继续 |

**关于两个不同的检查数字**：5,124 与 5,111 对应的是两个不同基线，不是笔误，也不是挑好看的写。界面收敛后有一部分检查随页面调整不再适用，最终发布基线为 5,111 项。两轮都是零失败、零报错。

**关于性能数字**：52,548.6 行/秒来自单次单表实测，不是通用基准。数据量、网络、表结构、索引与目标库负载都会改变结果，**请勿直接用它做容量规划**，建议在您自己的环境复测。

## 4　真的测出了问题，也真的修了

发布前在真实数据库上发现 4 项缺陷，全部修复，并在最终版本上重新验证：

| 现象 | 处理 | 最终复测 |
|---|---|---|
| 跨时区场景下时间字段偏移 8 小时 | 改为跟随数据库会话时区 | 时间偏差归零 |
| 长时间断网后恢复，源库把同步端误判为重复连接而停车 | 改为自动更换连接标识后重试 | 模拟断网 2 分钟后 14 秒追平，无缺失、无多余、无内容不一致 |
| SQL Server 实时捕获的实例发现引用了不存在的字段 | 修正发现方式 | 真库验证通过 |
| 另一种时间精度在跨时区下仍有偏差 | 统一时间基准 | 复测偏差归零 |

把这段写出来，是因为一套**从未在真实数据库上出过问题**的同步工具，通常只是没被认真测过。缺陷本身不可怕，修完不留证据才可怕。

## 5　您的数据库会被怎么对待

- **只读优先**：默认的定时增量不读取源库日志，只需要一个只读账号。选用秒级实时同步时，才需要数据库管理员开启相应日志并授权。
- **先体检，再动手**：正式启动前先检查连接、权限、表结构与对象范围，给出可执行的处理建议，而不是直接开始写。
- **只读试跑**：可以先跑一遍不写入目标库的试跑，看清会发生什么，再决定是否正式启动。
- **高风险操作二次确认**：重新建立同步起点、停止任务等动作，需要填写原因并输入任务名确认。
- **结构变化自动暂停**：源表结构发生漂移时暂停并提示，不静默继续写入。
- **凭据加密、本地留存**：连接凭据加密保存在本机，配置与运行记录不上传外网；产品可完全离线运行。
- **动作留痕**：谁在什么时间执行了什么动作，有记录可查；重复点击不会产生重复执行。

---

## 6　出问题时，一条完整的退路

1. **启动前**：体检 → 只读试跑 → 确认后才正式启动。
2. **运行中**：问题与动作中心把异常翻译成可执行的处理建议，并说明依据；处理动作带防重保护。
3. **要回退**：每阶段验收记录里都写好了顺序 —— 先停应用 → 恢复数据 → 换回旧程序 → 启动并验证连接与任务。**如果数据结构已经升级，必须先回数据再换程序，顺序不能反**，否则旧程序读不了新结构。
4. **跑完之后**：任务完成时会生成一份固定不变的完成报告，可导出 HTML 与 PDF 留档。事后复核看到的内容，与当时完成时一致，不会因为后来业务状态变化而变样。

## 7　如实披露：已知限制与选型前请自查

下面这些是我们**没做、没测完或需要您配合**的部分。列出来，是为了让您在正式切换前有一次主动判断的机会，而不是上线后才发现。

| 项 | 说明 | 给您的建议 |
|---|---|---|
| 长时间连续运行 | 一次计划 24 小时的实时同步稳定性观察，因中途环境停机中断，之后未再补跑。**本项未通过验证，也不作为发布结论的一部分** | 正式切换前，请用您自己的数据在目标环境连续观察一个完整业务周期 |
| 较老的数据库版本 | PostgreSQL 9.6 未纳入本轮验证矩阵，本轮实测的是 16 | 若使用较老版本，先做小范围试跑 |
| 实时同步的前置条件 | SQL Server、Oracle、PostgreSQL 的实时同步需要管理员预先开启日志并授权；Oracle 还需专用账号与视图权限 | 把这项排进实施计划，避免上线当天卡在权限上 |
| 容器化部署 | 本轮验证在本机直连真实数据库的环境完成，自动化检查未覆盖容器部署方式 | 容器场景建议先做一轮独立验证 |
| 界面样式 | 界面以实际交付版本为准 | 建议先装试用版确认观感 |

**选型前请确认这几件事**（不是说一定不行，是说本轮没把它们列为已验证范围）：

- 源表没有主键或唯一键，却需要按行识别增量变化 → 建议先整理主键再评估。
- 要求毫秒级端到端延迟，或多主双向写入 → 请先做针对性验证。
- 单表数据量远超本轮实测的 10 万行 → 性能请按您的实际表结构复测。

## 8　和免费工具怎么选

市面上有成熟的开源与免费同步工具，功能覆盖很广，很多场景下完全够用。我们**不建议用「功能更多」来说服您换工具**，也不认为免费等于不可靠。

| 您的情况 | 更合适的选择 |
|---|---|
| 临时搬迁、内部分析、有专人能自己看日志排障 | 免费开源工具通常够用，成本更低 |
| 要进生产、要过验收、信息科没有专职数据库管理员 | 重点看对方能不能提供验收记录、回滚步骤与明确的责任主体 |
| 数据出错会影响业务对账、监管报送或割接窗口 | 要求先做只读试跑，并把完成报告写进交付物 |

评估任何工具（**包括我们**）时，建议要求对方现场回答三个问题：

> 出问题时怎么定位？　怎么退回去？　谁签字负责？

答不上来的，功能表再长也别进生产。

## 9　升级、支持与责任主体

- **升级顺序**：停止旧程序 → 完整备份数据目录 → 替换程序文件 → 首次启动先核对已建连接与任务列表 → 确认无误后再启动同步任务。升级过程不会主动改动业务数据库。
- **完整性校验**：安装包提供 SHA-256 校验值，下载后建议先核对再用。
- **授权与责任**：灵渠为专有软件，保留所有权利，商业使用需取得授权。与纯社区项目不同的是，出问题有明确的责任主体与技术支持渠道。
- **获取帮助**：产品内「报告问题」入口会自动附带脱敏后的诊断信息；社区交流与常见问题见 <https://bbs.zzzmxxkj.com>。
